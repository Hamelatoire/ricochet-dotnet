# Generate release notes from merged pull request titles

Every merge to `main` publishes the next patch release, as [CLAUDE.md](../../CLAUDE.md) explains, so releases happen often and are written in a hurry. Their notes are written by hand, if at all, and a person reading a release can't easily see what changed. Pull request titles are already written in plain language, one per change. We will generate the release notes from the titles of the pull requests merged since the last tag, grouped by the kind of change, and attach them to the release.

## Decisions within this

- **Titles are the source:** each merged pull request contributes its title, so the notes match what the team already wrote for review.
- **Grouped by kind:** changes are grouped into features, fixes, documentation and internal changes, from a label or a title prefix, so readers find what matters to them first.
- **Pull request numbers are linked:** each entry links to its pull request, so the change can be read in full.
- **Generated, then checked:** the notes are generated by the release workflow and can be edited by hand before publishing, so a poor title doesn't have to be published as it stands.

## Considered Options

- **Write the notes by hand:** the most readable, but it doesn't happen on every patch release.
- **Publish raw commit messages:** automatic, but commit messages are less careful than titles and include merge noise.
- **No notes, only the tag:** nothing to maintain, but people can't see what a release changed.

## Consequences

- Pull request titles now matter for the notes, so the review checklist should name the title as part of the change.
- Documentation-only pull requests appear in the notes as well, which the grouping makes clear.
- The workflow needs permission to read pull requests, which must be granted with the least access needed, in line with ADR 0078.
